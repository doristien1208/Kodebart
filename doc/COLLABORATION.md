## 0. 每輪協作流程

本檔是唯一的跨工具溝通紀錄，不再另建重複的交接文件。

1. Claude 開始一輪前先讀本文件的「目前階段」「工程任務」「尚待決定」。只處理本輪明列的範圍，不順手展開下一階段。
2. Claude 完成後直接在「Claude 實作回報」新增一筆，列出修改檔案、完成行為、資料／存檔變更、已知限制及需要決定的問題。
3. 使用者通知 Codex 覆核。Codex 每一輪開始時先完整讀本文件的新回報，再讀取對應程式與資料。
4. Codex 只做程式碼、資料、文案與需求符合度覆核，不負責操作測試，也不重複執行 Claude 已做的測試。檢查結果寫入「Codex 檢查結果」，問題改寫成可直接交辦給 Claude 的工程任務。
5. 使用者負責實際操作、節奏、視覺與整體遊戲體驗測試；回饋與「通過／需修改」記錄在「使用者試玩回饋與驗收」。
6. 只有使用者明確驗收後，該小階段才可標為完成並進入下一輪。

若 Codex 在設計十天內容、資料量、敘事揭露或玩法規則時遇到會改變方向的問題，必須先停下來詢問使用者，不自行定案。

## 3. 使用者已確認的設計與限制

### 遊戲與敘事

- 遊戲名稱為 KodeBart，中文公司名稱為「柯迪巴特」。
- Web 劇情向遊戲，以角色扮演、調查、資料操作、選擇與延後後果為核心；玩法必須與系統架構、程式或資料處理有關。
- 核心命題：每個看似合理的行為都可能影響他人；流程與系統顯示成功，結果仍可能錯誤。不要直接把「語法正確、邏輯錯誤」當成教學答案告訴玩家。
- 主角是普通人類員工，不是英雄，沒有改寫世界因果或任意修改系統的權限。
- 選擇後果不立即公開；透過較晚出現的八卦、報告、新聞等片段讓玩家自行拼出關聯。
- 可保留內部隨機判定；結果可能受到制度或人為干預，但不向玩家直接公開操控機制，也不把所有隨機都寫成陰謀。
- 故事沒有救贖或快樂結局，後果可能不可逆；公司表面仍維持友善、平等與正常上班氛圍。

### 世界觀與 0102

- 柯迪巴特對外宣稱平等友善，實際上控管、抓捕、實驗或奴役巴特族，另有軍用改造計畫。
- 人類有自己的姓名；同事正常用名字稱呼，主角辦公室沒有巴特族員工。
- 0102 是女性巴特人與主要角色之一，目前沒有設定名字，不可擅自命名或解釋她為何沒有名字。
- 童年時 0102 曾在邊界主動幫助迷路的主角並給他食物；事件被監視器拍到，之後她被柯迪巴特以莫須有罪名抓走。
- 上述因果是作者層級設定，不代表玩家一開始知情。不得安排主角立即認出 0102，也不得提前公開完整因果或軍用計畫。

### 技術與視覺

- 規劃方向為 Angular、Tailwind CSS、p5.js 與 Node.js；Cloud Run 是未來選項，不代表目前已完成。
- 不自行加入 SSR 或大幅改造架構。
- 兩天 Demo 的目前試玩方向已獲使用者確認，可以作為階段一基礎；階段一最終目標是完成 **10 天可遊玩內容**。
- 現有資料處理量需要增加，不能讓主要遊玩只剩少量紀錄與短暫點選。
- 工作頁應讓玩家感覺正在操作一台電腦上的公司內部系統平台，而不是一般網站或宣傳頁。
- 頁面與系統模組切換需要加入過渡效果，但不得把每次切換做成恐怖故障或影響工作操作。
- 既有開始頁整體設計已獲使用者肯定；後續要求包含窗外落雨、走廊燈光閃爍，以及本輪主標題 Glitch。
- Glitch 只作用於主標題，保留其字體、位置與大小；單次維持約 200–350ms、水平錯位 1–3px 並帶輕微青色色差，關閉動態及 `prefers-reduced-motion` 時停止。原本 5–10 秒間隔已被使用者要求縮短；第四輪先以隨機 3–6 秒作為試作值，仍待使用者試玩校準。
- 目前動態雨不得穿過窗框、牆面、植栽、家具或其他室內前景。若完整靜態背景無法只靠長方形區域正確分離，應以對齊原圖的遮罩限制雨層；不能把「座標對齊」視為「雨只在室外」。
- 走廊燈光與標題 Glitch 的出現頻率都要比第三輪更密集；第四輪走廊短促閃爍先以隨機 2–4 秒為試作值，亮度與單次長度先保持第三輪數值，避免同時改太多變因。
- 第一輪不顯示種族欄位或 string／int 教學；玩家核對「人員編號」，姓名只用一般文字顯示。0102 顯示「姓名：未登記」「人員編號：0102」，前導零須在提交、存檔與重新載入後保留。
- 第一輪指定文字：操作說明「請依來源資料核對人員編號，完成歸檔。」；留空「請填寫人員編號。」；不符「請依來源資料填寫人員編號。」；成功「歸檔完成。」
- 第一輪不新增額外警告、主角疑心旁白或姓名缺漏原因；保留既有提交流程、選項、分支與後續事件紀錄。

### 階段一十天結構與訊息系統

- Day 1–5 先維持歸檔類工作，但每天必須增加資料量、規則或資料關係，不能只替換姓名後重複同一張表單。
- Day 3 起可開始出現八卦與日常對話；內容仍要像正常職場，不能讓每位同事、每個頻道都刻意顯得邪惡或可疑。
- 訊息模組要能容納「部門大群」「同事小圈圈群」與個人訊息，操作方式可參考 Slack／Teams 的頻道與對話列表，但視覺仍沿用柯迪巴特內部系統。
- 訊息有新內容時使用一般 Web 常見的紅點提示；紅點是未讀狀態，不是預先警告某則訊息很重要。
- Day 6 起改用新的資料集與資料操作；目前同意的玩法方向包含欄位映射、去重／合併、批次篩選與排序、版本差異及交接封存。這些是玩法骨架，具體案件、人物與正式文本仍屬提案，需另輪確認。
- 玩家選擇造成的訊息、報告與新聞應在之後解鎖；查看同一頻道或重新整理不能重新抽取隨機結果。

### 可維護性

- 大量遊戲文本不得繼續直接寫在 Angular 元件或單一 TypeScript 常數檔中。TypeScript 負責型別、規則、狀態與資料轉換；可編輯文本與結構化內容改由 JSON 為主，長篇文件必要時使用 Markdown。
- 遊戲內容需有穩定 ID，讓訊息、人物、頻道、資料紀錄、附件、條件與事件可以互相引用；不得依顯示文字、陣列索引或姓名當作存檔識別。
- 元件化以「有獨立責任、可重用或可獨立理解」為拆分依據，不要求每個小標籤都做成元件，也不在本輪打造通用遊戲引擎。
- 正式 Angular 畫面元件使用外部 `templateUrl`；有元件專屬樣式時使用外部 `styleUrl`／`styleUrls`。TypeScript 檔只保留元件 metadata、狀態與行為，不再把整段 HTML 或 CSS 塞入 inline `template`／`styles`。Tailwind class 留在 HTML，全域 token 與共用規則留在既有全域 CSS；沒有專屬樣式的元件不必建立空 CSS 檔。

### 素材與 UI 實作政策

- UI 能以 HTML、CSS、TypeScript 或 Canvas 完成時，優先用程式碼，不為裝飾性框線、表格、狀態燈、掃描線或轉場另外生成圖片。
- 只有程式碼無法合理完成、且確實能提升場景或敘事辨識度時，Codex 才補生成素材。
- 每一輪最多生成 **2 個素材**；未使用的額度不累積到下一輪。
- 新素材放入 `public/assets/`，檔名需可辨識用途，並在本文件「素材紀錄」記下來源、用途、使用位置與是否已獲使用者接受。
- 不生成 0102 的未定外觀、不替未定角色定型，也不把作者層級秘密做成提前劇透的素材。

負責方：Claude

#### 發現並交辦第五輪的問題

1. **跨日訊息歷史會消失**：`cond.day.1` 與 `cond.day.2` 使用相等判斷，`unlockedMessages()` 每次只保留當天條件成立的訊息。進入 Day 2 後，Day 1 私訊不會留在同一對話歷史。已交辦 KB-R5-01。
2. **紅點外觀不符已確認需求**：`UnreadBadgeComponent` 使用直角矩形 class，Claude 也在回報中稱為「直角小方塊」。使用者指定的是 Web 常見紅點；這是需求修正，不再列為待決定。已交辦 KB-R5-01 改為圓形。
3. **內容必要欄位沒有真正受 schema 保護**：`validate-content.ts` 對 task／document／transition 的 `text` 只檢查是否為物件，`text.ts` 再以泛型雙重斷言取值。像 `heading`、`choices.review` 或 `dialog.response.ask` 缺漏時仍可能通過內容驗證。已交辦 KB-R5-02。
4. **十天邊界仍只完成一半**：`GameStateService.records` 與 `record()` 仍使用跨日全域 `RECORDS`；`game.day()`、`WorkViewComponent`、Workbench 的 `Record<1 | 2>` 文本、`Phase`、路由及 archive 規則仍固定 Day 1／Day 2。現在直接加入 Day 3 紀錄會提前混入 Day 1 佇列，且核心狀態無法表示第三日。已交辦 KB-R5-03。
5. **存檔的目前日仍由 legacy phase 猜測**：`SaveRepository.load()` 在驗證 v3 前先用 phase 推 `batchId`，而非以存檔自己的 `dayId` 與內容目錄解析；schema 也未驗證 dayId 與 phase 是否一致。兩日資料恰好映射到同一批次，所以目前不會顯性失敗，但無法安全延伸 Day 3。併入 KB-R5-03。
6. **舊訊息 API 尚未移除**：畫面已改走頻道 API，但 `content/text.ts` 仍保留 `MESSAGES.author/day1/day2Lead/day2SmallTalk` 給舊測試使用，形成兩套入口。已交辦 KB-R5-02 在更新測試後移除。
7. **元件檔案仍混合三種責任**：盤點到 `src/app` 的正式畫面元件全部使用 inline template；其中封面、封面場景、封面標題、訊息頁與工作台另把元件 CSS inline 在 `.ts`。這不影響執行，但會讓後續十天畫面修改時 TypeScript、HTML 與樣式互相干擾。依使用者回饋交辦 KB-R5-04。

## 10. 本階段試玩方式

在專案根目錄執行：

```bash
npm start
```

瀏覽器開啟 `http://localhost:4200/`。若瀏覽器留有舊進度，按「開始遊戲」並在確認視窗選擇覆蓋，才能從 Day 1 重新測試。

建議檢查順序：

1. 停留開始頁至少 10–15 秒，觀察標題是否只在短時間局部錯位，且選單不移動。
2. 開啟「設定」，關閉動態後再停留至少 10 秒，確認 Glitch 停止；重新開啟後應恢復排程。
3. 觀察右側窗外是否有落雨、走廊亮框是否會呼吸與偶爾閃一下。兩者都應該只出現在該區域，選單與左側牆面不得跟著閃。步驟 2 關閉動態後，落雨與燈光也應一併停止。
4. 開始遊戲，先看「本日資料佇列」：每列都應有「待處理」或「✓ 已完成」文字，目前選取的那列有 ▸ 標記。切到 0102：確認姓名為「未登記」、畫面沒有種族或 string／int 說明。
5. 看導航列「訊息」旁的紅點。先只進訊息頁不要點頻道，紅點應該還在；點開「林予安」後紅點消失；重新整理後不應復活。進到第二天後紅點會因為新訊息回來。
6. 在工作台切換「工作／訊息／公告」，確認只有主要內容區淡入，頂列、左側導航與右側摘要欄不動。狀態列會隨內容長短上下移動，這是既有版面行為（關閉動態時同樣如此），若覺得干擾請回報。
7. 人員編號先留空，再填 `102`，最後填 `0102`，依序核對兩個錯誤提示與成功預覽。
8. 選擇任一缺值處理方式並確認歸檔；重新整理頁面，確認 `0102` 與已完成狀態仍在。
9. 完成三筆資料後進入第二天，觀察是否能自行察覺摘要與昨日副本的關係；記錄哪些地方像遊戲、哪些地方只像填表。
